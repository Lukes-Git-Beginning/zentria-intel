#### GigaToken — ~1000× schnellere LLM-Tokenisierung via SIMD (Open Source, MIT) (n_sources:1, score:0.63)

**Quellen:**
- [GitHub: marcelroed/gigatoken](https://github.com/marcelroed/gigatoken/) (22. Jul, HN #404 Punkte)

**Was passiert:**
GigaToken ist ein Drop-in-Replacement für HuggingFace Tokenizers mit SIMD-Optimierung (Single Instruction Multiple Data). Performance auf AMD EPYC 9565 (144 Cores): **24,53 GB/s = 989× schneller als HuggingFace.** Auf Apple M4 Max: 1,38–8,79 GB/s je nach Tokenizer-Komplexität. Unterstützt 30+ Modelle: GPT-2, Qwen, Llama 3/4, Phi-4, DeepSeek, GLM. SentencePiece-basierte Tokenizer sind explizit weniger optimiert. MIT-Lizenz, Rust-Implementierung.

Kernoptimierung: Pre-Tokenization über SIMD statt Regex-Engine, Caching von Pretoken-Mappings, reduzierte Python-Rust-Bridge-Overhead.

**Was bedeutet das für Cosmi?**
Für Cosmi-AI kurzfristig: Bei Batch-Verarbeitung (AI-Import, Bulk-CRM-Analyse, Reporting-Summaries) ist Tokenizer-Speed ein realer Bottleneck. GigaToken als Drop-in würde Preprocessing-Latenz auf CPU-gebundenen Inference-Pipelines erheblich senken. Priorität: niedrig bis Cosmi-AI-Pipeline-Architektur konkret steht. Relevanz steigt bei lokalen Modellen (On-Premise-Tier).

#### Text-to-SQL in der realen Welt — heterogene DBs sind viel schwieriger als Benchmarks (n_sources:1, score:0.41)

**Quellen:**
- [CACM: If You Think You Can Do Real-World Text-to-SQL](https://cacm.acm.org/blogcacm/if-you-think-you-can-do-real-world-text-to-sql/) (403 bei Fetch — Kontext aus WebSearch)

**Was passiert:**
CACM-Artikel (Quelle via Forschungs-Web-Suche ergänzt): Bestehende Text-to-SQL-Benchmarks sind SQLite-zentriert — reale Produktionsdatenbanken (PostgreSQL, MySQL, MSSQL, Oracle) haben erheblich andere Dialekte, Typensysteme, Funktionen. UniQL-Benchmark: 24.544 dialektspezifische Queries über 16 SQL-Dialekte aus 1.534 NL-Questions zeigt systematisch niedrigere Accuracy bei Cross-Dialect-Transfer. Hauptfehlertypen: fehlerhafte JOINs, falsche Aggregationen, fehlende Filter, Syntax-Fehler. Generation-Selection-Gap: Modelle können korrektes SQL generieren, identifizieren es aber nicht als korrekt.

**Was bedeutet das für Cosmi?**
Cosmi-Datenmodell wird komplexe Multi-Modul-Schemas haben (CRM × Helpdesk × Accounting in einer PostgreSQL-Datenbank). Text-to-SQL für natürlichsprachliche Reports wäre eine attraktive Cosmi-AI-Feature. Aber: Benchmark-Performance ≠ Feldperformance auf heterogenen Schemas. Cosmi müsste einen eigenen Schema-Annotierungs-Layer aufbauen (Tabellenbeschreibungen, Business-Kontext pro Spalte) bevor Text-to-SQL produktionsreif ist. Kein Shortcut über generische Modelle. Pfad: `backend/internal/ai/text-to-sql/schema-context/` (Voraussetzung vor Feature-Launch).

### tech-infra

#### The Startup's Postgres Survival Guide — Connection Pooling, Vacuum, Bloat (n_sources:1, score:0.58)

**Quellen:**
- [Hatchet: Postgres Survival Guide](https://hatchet.run/blog/postgres-survival-guide) (22. Jul, HN #338 Punkte)

**Was passiert:**
Drei Kern-Empfehlungen für Production-PostgreSQL:

1. **Connection Pooling:** Externer Pooler (PgBouncer) für teure Connection-Overhead-Verwaltung. In-Process-Alternativen (pgxpool für Go) als Fallback. "Connection Storms" sind schwer zu debuggende Edge Cases — Pooler verhindert sie.
2. **Autovacuum-Tuning:** Default-Settings zu konservativ für High-Write-Szenarien. Autovacuum >1h = Konfigurationsproblem. Risiko ohne Tuning: Transaction-ID-Wraparound = katastrophischer Downtime. Autovacuum aktualisiert gleichzeitig Query-Planner-Statistiken — doppelter Benefit.
3. **Bloat-Management:** Table Bloat → `pg_repack` (nicht `VACUUM FULL`, das sperrt). Index Bloat → `REINDEX INDEX CONCURRENTLY`.

**Was bedeutet das für Cosmi?**
Cosmi mit 14+ Modulen auf einer Datenbank: Connection-Pooling ist von Tag 1 erforderlich (nicht "wenn wir skalieren"). PgBouncer als Default in Cosmi-Docker-Compose. Autovacuum-Konfiguration in Cosmi-Deployment-Docs explizit adressieren — fehlt bei vielen Self-Hosted-Setups. `pg_repack` als Maintenance-Runbook-Eintrag. Pfad: `deploy/docker-compose/` + `docs/ops/postgres-tuning.md`.
