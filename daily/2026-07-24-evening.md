**Quellen:**

- [SOC Prime: Lazarus Group Uses Git Hooks to Hide Malware](https://socprime.com/active-threats/lazarus-group-uses-git-hooks-to-hide-malware-dprks-contagious-interview-and-taskjacker-campaign-is-now-hiding-its-second-stage-loader-inside-git-hooks-that-download-invisibleferret-and-beavertail-malware/) (Threat Intelligence)
- [Microsoft Security Blog: Contagious Interview — Malware delivered via fake developer job interviews](https://www.microsoft.com/en-us/security/blog/2026/03/11/contagious-interview-malware-delivered-through-fake-developer-job-interviews/) (März 2026)
- [TrendMicro: Void Dokkaebi — Fake Job Lure via Code Repositories](https://www.trendmicro.com/en_us/research/26/d/void-dokkaebi-uses-fake-job-interview-lure-to-spread-malware-via-code-repositories.html)

**Was passiert:**
Die "Contagious Interview"-Kampagne der nordkoreanischen Lazarus Group (DPRK) hat 2026 eine neue Eskalationsstufe erreicht: **Git pre-commit- und post-checkout-Hooks** werden als Payload-Carrier missbraucht. Ablauf: Recruiter-Impersonation bei Crypto/AI-Unternehmen → Kandidat klont Repository für "Coding Challenge" → beim ersten `git checkout` oder `git commit` feuert ein präparierter Git-Hook und lädt plattformspezifischen Second-Stage-Loader (InvisibleFerret macOS, BeaverTail Windows/Linux) herunter. Der Hook ist außerhalb des Standard-Diff sichtbar, aber in der `.git/hooks/`-Verzeichnisstruktur — bei schnellem `git clone` übersehen.

**Ausmaß (März–Juli 2026):** >750 infizierte Repositories identifiziert, >500 bösartige VS Code-Task-Konfigurationen, 101 Commit-Manipulation-Tools. Ziele: Entwickler-Credentials, Crypto-Wallets, Source-Code-Exfiltration. Hauptzielgruppe: Web3/AI-Unternehmen — aber Angriffsmuster nicht Web3-spezifisch.

**Relevanz für Cosmi-Entwicklungsumgebung:**
Das HN-Post-mortem (#309) ist von einem Entwickler, der den Angriff fast nicht bemerkt hätte — der Git-Hook lud eine Payload in einem npm-Postinstall-Skript nach. **Konkrete Schutzmaßnahmen für Cosmi-Dev-Team:**
1. `git config core.hooksPath /path/to/approved-hooks` — Hooks ausschließlich aus versioniertem, review-pflichtigen Verzeichnis laden
2. Pre-commit-Hook-Review als PR-Pflicht (alle `.git/hooks/`-Änderungen erfordern Senior-Review)
3. npm-Postinstall-Skripte in `package.json` auditieren (`--ignore-scripts` als Dev-Default bis Review)
4. Keine Repository-Clones von unbekannten Quellen auf Entwicklungs-Maschinen mit Produktions-Credentials

**Was bedeutet das für Cosmi?**
Cosmi-Entwicklungsteam hat erhöhtes Risiko, weil (a) AI/Crypto-Adjacenz (Lazarus-Primärziel), (b) aktive GitHub-Nutzung, (c) potenzielle Open-Source-Beitrags-Workflows. Modul-Pfad: `docs/security/dev-environment-hardening/git-hook-policy.md` (erstellen). Keine unmittelbare Produktions-Relevanz für Cosmi-Endkunden, aber Dev-Team-Supply-Chain-Risiko ist real.

#### BSI WID-SEC-2026-2472: Budibase — CVSS 10.0 NoSQL-Injection + SSRF in AI-Extract (n_sources:2, score:0.59)

**Quellen:**
- [BSI WID: WID-SEC-2026-2472](https://wid.cert-bund.de/portal/wid/securityadvisory?name=WID-SEC-2026-2472) (22. Jul)
- [IONIX Threat Center: CVE-2026-54350](https://www.ionix.io/threat-center/cve-2026-54350/) (Deep-Analysis)

**Was passiert:**
Drei CVEs in Budibase <3.39.12:

**CVE-2026-54350 (CVSS 10.0, Critical) — Unauthentifizierte NoSQL-Operator-Injection:**
Angriffs-Vektor: HTTP-Request ohne Auth → `enrichContext()` substituiert attacker-controlled JSON-Parameter direkt in rohen Query-Body vor `JSON.parse()` → Angreifer kann MongoDB-Operatoren (`$gt`, `$where`, `$regex`) injizieren → **vollständiger Mass-Read + Mass-Write über gesamte Datenbank in einem Request**. Root-Cause: `validateQueryInputs()` blockt nur Handlebars-Marker (`{{`, `}}`), escapet aber nicht JSON-Metacharakter (`"`, `{`, `}`). Betroffene Datasources: MongoDB, CouchDB, Elasticsearch, DynamoDB-PartiQL, REST-JSON. **SQL-Datasources (PostgreSQL, MySQL) nicht betroffen** — Bind-Parameterisierung schützt strukturell. Fix: Upgrade auf ≥3.39.12.

**CVE-2026-41428 (High) — File Manipulation (Authenticated):** Authentifizierter Angreifer kann Dateipfade manipulieren → Server-seitiger File-Write. Voraussetzung: Budibase-Account, aber Low-Privilege reicht.

**CVE-2026-45548 (High) — SSRF in AI-Extract (fehlendes IP-Blacklist):** Budibase's AI-Daten-Extract-Feature macht Server-seitige HTTP-Requests ohne IP-Whitelist → Angreifer kann interne Netzwerk-Ressourcen ansprechen (AWS IMDSv1, interne APIs). Besonders kritisch in Cloud-Deployments ohne IMDSv2.

**Was bedeutet das für Cosmi?**

*Direkte Relevanz für Cosmi-Formulare-Modul:* Budibase ist ein direkter Konkurrent im Low-Code-Forms/App-Builder-Segment. CVSS 10.0 bei unauthentifiziertem Mass-Data-Write ist ein **katastrophaler Modul-Design-Fehler** — nicht ein Edge-Case-Bug. Cosmi's struktureller Vorteil: PostgreSQL-Backend mit Bind-Parameterisierung schützt gegen diesen spezifischen Angriffsvektor. **Content-Opportunity (ohne Naming):** Cosmi-Formulare-Blog "Security-by-Design in Form-Builders: warum der Datasource-Typ entscheidend ist" als AEO-Asset — erklärt den Unterschied zwischen Document-Store (MongoDB) und relationaler DB (PostgreSQL) im Security-Kontext, ohne Budibase zu nennen. Modul-Pfad: `backend/internal/formulare/security-audit/`, `marketing/content/form-security-by-design/`.

*Strukturelle Lektion für Cosmi:* Die SSRF-Lücke im AI-Extract-Feature zeigt ein Muster: **AI-Features, die externe HTTP-Requests machen, brauchen strikte IP-Allowlists von Tag 1.** Cosmi-AI-Features (falls sie Web-Lookups oder externe API-Calls machen werden) müssen diesen Schutz eingebaut haben. Modul-Pfad: `backend/internal/ai/security/ssrf-protection/`.

#### The Startup's Postgres Survival Guide — Connection Pooling, Vacuum, Bloat (n_sources:1, score:0.58)

**Quellen:**
- [Hatchet: Postgres Survival Guide](https://hatchet.run/blog/postgres-survival-guide) (HN #338)

**Was passiert:**
Operatives Praxis-Handbuch für PostgreSQL in Produktionsumgebungen. Kern-Themen:
- **Connection Pooling:** PgBouncer als Proxy zwischen App und PostgreSQL — kritisch wenn Cosmi-Applikation viele kurzlebige Verbindungen öffnet (typisch bei Next.js/API-Routes-Pattern). Transaction-Pooling als Default für Web-Apps.
- **Autovacuum-Tuning:** `autovacuum_vacuum_scale_factor = 0.01` für große Tabellen (Default 0.2 ist zu aggressiv für Tabellen mit Millionen Rows). `autovacuum_analyze_scale_factor = 0.005` empfohlen.
- **Table Bloat:** `pg_repack` statt `VACUUM FULL` — kein Lock Table bei `pg_repack`, ermöglicht produktionsfreundliche Bloat-Bereinigung. Bloat-Detection via `pgstattuple` oder `pganalyze`.
- **Index Bloat:** `REINDEX CONCURRENTLY` für Index-Rebuild ohne Table-Lock.
- **Dead-Tuple-Monitoring:** `pg_stat_user_tables.n_dead_tup / n_live_tup` als Bloat-Ratio-KPI.

**Was bedeutet das für Cosmi?**
Als PostgreSQL-basiertes Multi-Modul-System (CRM + Helpdesk + Buchhaltung in einer DB) wird Cosmi mit Wachstum diese Operationsebene treffen. **Direkt anwendbare Maßnahmen:**
1. PgBouncer von Anfang an in `docker-compose.production.yml` einplanen — kostenlos, eliminiert Connection-Exhaustion-Hotspot
2. Autovacuum-Parameter für Cosmi-Kern-Tabellen dokumentieren (insbesondere `crm_leads`, `helpdesk_tickets`, `rapporte_entries` — High-Write-Tabellen)
3. `pg_repack`-Runbook im Ops-Playbook verankern
